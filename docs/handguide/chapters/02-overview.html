System overview

The workbench is a scorer's console and a statistics engine in one window, with a small host program that keeps the league on disk and never lets the window show a result that is not recorded.

The workbench in brief

An operator starts the Photon host. The host checks that its own code is the code the release sealed, takes the data folder for itself, opens the league, identifies this laptop and gives it its own static loopback address, listens on that address only, and opens the workbench in a Chromium-family window with a profile of its own. The window loads the league from the host and replays every game's ledger through the engine. From then on the engine runs in the window: each line the scorer types is lexed, compiled to frames and applied by the game actor in memory, and whatever the line changed — new ledger entries, a changed registry — is sent to the host, which checks it, writes it, syncs it to disk and only then answers. The window shows the line's result after that answer, and only after it.

Two editions

RINK-VT exists in two editions. They share the engine — the language, the frame, the actor, the models and HK001 — and the static loopback lease algorithm, and differ in what surrounds the engine.

Components of the LK/Vexa edition

The renderer and the host are separate processes ({{ref:fig-components}}). The renderer holds the league in memory and does all the computing; the host holds the league on disk and does all the keeping. Neither trusts the other further than it must: the host checks every ledger entry against the engine's own seals before it writes it ({{ref:store-checks}}), and the window treats a refused commit as the truth and reloads ({{ref:refused}}).

From a typed line to a statistic

  1. Lexing and assistance. As the scorer types, the lexer of the language classifies the line (empty, incomplete, valid or invalid), offers grey ghost text and candidates, and names the reason a line cannot become valid ({{ref:input-assist}}).

  2. Compiling. On Enter the line is compiled to one or more 64-byte frames: a UUIDv7, the keystroke onset and commit times in nanoseconds, the game's hash, a Lamport counter, the team, player, stat and modifier codes, the coordinates and a CRC-32C ({{ref:frame}}).

  3. Applying. The game actor applies the frames of the line atomically: all or none. It latches the clock at the keystroke, binds assists to the open goal, infers rebounds and rushes, tracks penalties, strength and stints, and computes expected goals ({{ref:actor}}).

  4. Recording. Each accepted frame is appended to the game's ledger in memory together with a 64-byte meta line (who typed it, when, from which loopback address). The window then commits the new entries to the host, which writes and syncs them ({{ref:recording}}).

  5. Deriving. Queries and models read the actors' state: Q BOX, Q XG, Q STINTS, standings and leaders, RAPM, GSAx, GAR/WAR, NHLe, heat maps, and the 109 HK001 inputs with their provenance ({{ref:queries}}, {{ref:models}}).

What is kept, and where

Everything durable is in the data folder ({{ref:data-folder}}): the registry (leagues, teams, players, games, notes), one ledger per game, the host's event ledger, the lease table and the window's browser profile. The renderer keeps nothing of its own: closing the window loses nothing that was recorded, and a window that is reopened loads the league again from the host. The program files are separate from the data folder and sealed by the release manifest ({{ref:manifest}}).

Design principles

Record before show
A command's result appears only after the host has synced what the command changed. A refusal is shown as NOT RECORDED and the window reloads, so it never shows what is not on disk.
Nothing unchecked is kept
Every entry the host writes passes the engine's CRC-32C seals and belongs to its game; every stored file is sealed or hash-chained; damage refuses to open and is named.
One engine
The engine's source files are the reference edition's {{reference}}, unchanged except for the options the reference edition added for a host that keeps the league ({{ref:engine-options}}) and the start frame, the whistle and the league overtime rules added in this edition ({{ref:clock}}, {{ref:overtime}}), which keep every earlier behaviour and pass the reference edition's 78 engine tests.
One folder, one host
A data folder is held by an exclusive lock; a second host is refused.
A sealed release
The host refuses to run code that the release did not seal.
Honest maturity
The contracts say OPERATIONAL only with the tests that show it, and the qualification names the platform it ran on ({{ref:contracts}}).
