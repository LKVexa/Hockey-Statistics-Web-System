Verification

A release, and a league, can be checked by anyone holding them, with the release's own tools and no network. This chapter gives the procedure, its acceptance criteria and the maintainer's release procedure.

The verifier

VERIFY_RINKVT.cmd (Windows) or VERIFY_RINKVT.sh (macOS, Linux) runs the host's verify command ({{ref:native-host}}). It takes five steps, reports each as PASS or FAIL with what failed, and writes nothing. The release is VERIFIED only when every step passes.

#StepWhat it checks
1ReleaseEvery file of the release, the executables among them, against RELEASE_MANIFEST.json (scope all): the lists of missing, changed and unlisted files must be empty
2Renderer bundleui/workbench.js and ui/workbench.html are exactly what engine/ and ui/ give, rebuilt in memory ({{ref:bundle}})
3ContractsEvery MSSL record valid and current, the qualification for this version and PASS, the JA21 sources well formed, their constants equal to the implementation's ({{ref:contracts}})
4Host self-testThe host checks itself in a scratch folder it removes afterwards: the CRC-32C check value; the device key and the lease vectors ({{ref:lease-vectors}}); a device file; a league written, reopened and verified, then damaged by one changed digit, which must be found; and, on a loopback listener of its own, the API's refusals (421, 403, 415, 400, 409, 405) and a commit round trip
5LeagueThe league in the data folder, read only: every seal and chain (skipped with a note while a host holds it); then this laptop's device and pinned address

Options: --data DIR checks another data folder; --device-file FILE reads another device file. The report begins with the version and the executable that made it:

RINK-VT {{version}} · LK/Vexa edition (Photon-hosted) · Photon host · native windows/amd64 executable · no Python, no Node.js
[1] release (… files against RELEASE_MANIFEST.json): PASS
[2] renderer bundle: PASS
[3] contracts ({{n_records}} MSSL records, {{n_ja}} JA21 sources, constants cross-checked): PASS
[4] host self-test (store, leases, device, HTTP guards): PASS
[5] league (12 games): PASS
    this laptop: device 786ccb4a · pinned 127.26.220.77

RINK-VT LK/Vexa edition: VERIFIED

The verifier does not run the test suite: the tests are Go tests and need the Go toolchain, which a computer that runs the workbench does not need and need not have. Their result is the qualification record, which step 3 requires to name this version with the result PASS; a maintainer runs them again with contracts qualify ({{ref:tests}}).

Procedure

  1. Obtain the release from its source, keeping its bytes ({{ref:getting-started}}).

  2. Run the verifier: VERIFY_RINKVT.cmd, or ./VERIFY_RINKVT.sh.

  3. Read the report. Step 1 names any changed, missing or unlisted file; step 3 any record or source that fails; step 4 any check of the host that fails; step 5 any damaged league file and line.

  4. Keep the report with the release, and the league's verification report with each backup.

  5. To check that the executables are those of the sources, rebuild them with the Go version that built them and compare their digests with the manifest ({{ref:build-from-source}}).

Acceptance criteria

VER-01Step 1 reports PASS: no missing, changed or unlisted file.
VER-02Step 5 reports PASS for the league, or that there is no league yet.
VER-03Step 2 reports PASS: the bundle matches its sources.
VER-04Step 3 reports PASS for every record and source, and the qualification names this version with the result PASS.
VER-05Step 4 reports PASS. The qualification record's scope says what its test run did not cover (the browser tests where no browser was available, other platforms); the release is qualified for what it covered only.

The release procedure

A maintainer who changes the release makes a new one in this order, because each step seals what the steps before it produced. The commands are the host's, run through RINKVT.cmd or ./rinkvt.sh.

  1. Change the sources (photon/*.go, ui/, engine/, the contract table in photon/contracts_table.go) and, if the version changes, photon/version.go.

  2. Build the executables: photon/build.cmd or photon/build.sh ({{ref:build-from-source}}).

  3. Bundle: bundle.

  4. Write the contracts: contracts write.

  5. Qualify: contracts qualify runs the whole test suite (go test -count=1 -v ./... in photon/) and writes contracts/mssl/90_qualification.mssl from its result. It must say PASS.

  6. Print the handguide if anything it describes changed: handguide ({{ref:handguide-build}}).

  7. Seal: seal writes RELEASE_MANIFEST.json.

  8. Verify: run the verifier on a fresh copy of the release, and publish the release with its report.

MNT-01A maintainer MUST NOT publish a release whose qualification is not PASS or whose verification fails.
MNT-02A maintainer MUST NOT raise a maturity in a contract without the evidence it names ({{ref:honesty}}).
MNT-03A maintainer SHOULD change the engine only in the reference edition and carry the change over, so that the two editions keep one engine.
MNT-04A change to a file format MUST change its format identifier (rinkvt.registry.v1, rinkvt.vec1-ledger.v1, the lease format number) and say how a league is brought over.

Building the executables

The release carries the executables, so building them is for maintainers only. photon/build.cmd (Windows) or photon/build.sh (macOS, Linux) builds all six with the Go toolchain, version 1.22 or newer, from go.dev: with CGO_ENABLED=0, so that no C compiler is involved and no C library is linked in; with -trimpath, so that no path of the building computer is recorded; and with -ldflags "-s -w -buildid=", so that there is no symbol table and no build identifier. The macOS executables for Apple silicon carry the ad-hoc signature the Go linker gives them, which that system requires; no executable is signed by a publisher.

The build is reproducible: the same sources and the same Go version give the same bytes, on any computer. The executables of this release were built with {{go_version}}, which go version names when given any of them. Anyone can therefore check a release's executables against its sources: rebuild them with that version and compare their SHA-256 digests with RELEASE_MANIFEST.json. After a deliberate change, seal records the new digests.

Printing this guide

The host's handguide command prints this guide to docs/handguide/RINK-VT_Handguide.pdf from its sources — the chapters in docs/handguide/chapters/ and the stylesheet — with the installed Edge, Chrome or Chromium, which it drives without a window over the browser's DevTools protocol; RINKVT_BROWSER names another. It reads the engine's tables by running the bundle in the browser, the test inventory from photon/*_test.go and the records from contracts/; prints the document until the page numbers of the contents and the cross-references settle; prints the running headers and footers as a second document and draws each of its pages over the matching page, marked as an artifact so that the document's tagged structure is unchanged; and adds the page labels, the bookmarks and the document information. --out FILE writes the guide elsewhere and --html FILE also writes the composed page. This revision was printed by {{chromium}}.
