Verification

A release, and a league, can be checked by anyone holding them, with the release's own tools and no network. This chapter gives the procedure, its acceptance criteria and the maintainer's release procedure.

The verifier

VERIFY_RINKVT.cmd (Windows), VERIFY_RINKVT.sh (macOS, Linux) or python -I -B tools/verify.py runs four steps and reports each as PASS or FAIL. The release is VERIFIED only when every step passes.

#StepWhat it checks
1Release and leaguephoton/rinkvt.py --verify-only: every file of the release against RELEASE_MANIFEST.json (scope all), and the league in the data folder, read only (skipped with a note while a host holds it)
2Renderer bundletools/bundle.py --check: ui/workbench.js and ui/workbench.html are exactly what engine/ and ui/ give
3Contractstools/contracts.py check: every MSSL record valid and current, the qualification for this version and PASS, the JA21 sources well formed, their constants equal to the implementation's ({{ref:contracts}})
4TestsThe test suite ({{ref:tests}}); the browser tests need Playwright for Python and a Chromium build and are skipped without them

Options: --data DIR checks another data folder; --mssl-verifier PATH also runs the MSSL Writers Corpus validator on every record; --quick leaves out the browser tests.

Procedure

  1. Obtain the release from its source, keeping its bytes ({{ref:getting-started}}).

  2. Run the verifier. With the MSSL corpus at hand, add --mssl-verifier <corpus>/tools/VERIFY_MSSL.py.

  3. Read the report. Step 1 names any changed, missing or unlisted file and any damaged league file; step 3 names any record or source that fails; step 4 names any failing test.

  4. Keep the report with the release, and the league's verification report with each backup.

Acceptance criteria

VER-01Step 1 reports "ok": true for the release, with empty missing, changed and unlisted lists.
VER-02Step 1 reports "ok": true for the league, or that there is no league yet.
VER-03Step 2 reports that the bundle matches its sources.
VER-04Step 3 reports PASS for every record and source, and the qualification names this version with the result PASS.
VER-05Step 4 reports no failure and no error. Skipped tests are acceptable only when their reason is that an optional tool (Playwright, the corpus validator) is absent, and the report then does not cover what they test.

The release procedure

A maintainer who changes the release makes a new one in this order, because each step seals what the steps before it produced.

  1. Change the sources (photon/, ui/, engine/, tools/, tests/, contracts table in tools/contracts.py) and, if the version changes, photon/host/__init__.py.

  2. Bundle: python -I -B tools/bundle.py.

  3. Write the contracts: python -I -B tools/contracts.py write.

  4. Qualify: python -I -B tools/contracts.py qualify runs the whole test suite and writes contracts/mssl/90_qualification.mssl from its result. It must say PASS.

  5. Build the handguide if anything it describes changed: python docs/handguide/build.py.

  6. Seal: python -I -B tools/seal_release.py writes RELEASE_MANIFEST.json.

  7. Verify: run the verifier on a fresh copy of the release, and publish the release with its report.

MNT-01A maintainer MUST NOT publish a release whose qualification is not PASS or whose verification fails.
MNT-02A maintainer MUST NOT raise a maturity in a contract without the evidence it names ({{ref:honesty}}).
MNT-03A maintainer SHOULD change the engine only in the reference edition and carry the change over, so that the two editions keep one engine.
MNT-04A change to a file format MUST change its format identifier (rinkvt.registry.v1, rinkvt.vec1-ledger.v1, the lease format number) and say how a league is brought over.
