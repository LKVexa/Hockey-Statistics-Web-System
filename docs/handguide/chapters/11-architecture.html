Architecture

Two processes, one boundary between them, and one folder on disk. This chapter maps the release onto that structure and follows a command through it.

Processes and trust boundaries

The renderer computes; the host keeps. The renderer reaches nothing but its own origin, the host, and the host trusts nothing a request says: it checks the request's Host, token, origin and form, and every ledger entry against the engine's own seals, before it writes. The host's failures are the renderer's truth — a refusal makes the window reload — and the renderer's failures cannot reach the disk unchecked.

The renderer bundle

The engine is a set of CommonJS modules written for Node.js. The host's bundle command places each module's source text, unchanged, in a function of a module table, and each data table (the Mathematical Corpus, the HTML5 entity table, the Go tables) in a data table, inside the loader. The loader resolves require as Node.js does for relative paths and provides the few built-ins the modules name: path, events, os, process, Buffer (on Uint8Array) and crypto hashing (SHA-1 and SHA-256 from the engine's own rink/shared/hash.js). It provides no file system: a module that would read a file is told that the renderer has none and that the host keeps the league. The bundle is ui/workbench.js: the loader with the engine, then the rink drawing, then ui/app.js. bundle --check rebuilds it in memory and compares, so a stale bundle is found by the verifier. No Node.js is used to build or to run the bundle: the engine's modules are only text to the host, and the browser runs them.

The engine's service takes four options a host uses — the first three added in the reference edition for this edition, the fourth in this release: registryData, a league to start from; preload, a function giving each game's stored ledger entries when the game opens; and store, a description of where the host keeps the league, which the service then reports as durable. With them the engine runs in memory and replays what the host stored, exactly as the reference edition replays its own ledgers.

The life of a command

A scored line passes through these modules, in order: the command line (ui/app.js) keeps the keystroke onset; the RINK mode of the command pack (commands/rink.js) hands the line to the lexer (hcl.js), which parses it; the compiler (wire.js) makes the frames; the in-process client (inproc.js) submits them to the service (service.js), which checks the clock skew and hands them to the game's actor (actor.js), which applies them atomically; the service appends each accepted frame and its meta line to the game's ledger; app.js commits the new entries to the host (server.go → store.go), waits for the answer, and the command pack prints the result through the terminal renderer (term/render.js). The game panel then redraws from the actor's state.

Concurrency

The renderer is single-threaded: one command runs at a time, and the window waits for a commit's answer before the next line's result. The host serves each connection concurrently, on a goroutine of its own; the store admits and writes one commit at a time under a store lock, the event ledger appends under a lock of its own, and a lease allocation takes the lease table's file lock. A verification takes the store lock, so it never reads a half-written commit.

Dependencies

The host uses the Go standard library only — net/http, net, net/netip, crypto/sha256, crypto/hmac, crypto/rand, hash/crc32, encoding/json, compress/zlib, os/signal, os/exec and syscall among them — with no third-party module (photon/go.mod requires none) and no cgo. It is compiled ahead of time into one executable per platform, so a computer that runs it needs no interpreter, runtime or package: no Python and no Node.js. The renderer is the installed browser, which also prints this guide; nothing else is used to build the guide either.
