Static loopback addresses for every laptop

Every laptop that uses RINK-VT receives one address of its own in the loopback network 127.0.0.0/8 and keeps it: on every network, in every league, after every restart and reinstall of RINK-VT. No two laptops ever hold the same address in one league, and none anywhere when they share a fleet register. The workbench listens on that address and records it with every line typed, so the audit trail says which laptop typed what — without an IP address ever being stored.

Purpose and principle

An IP address is not a laptop. A laptop takes a new address on every network it joins — the club's Wi-Fi, the arena's, a phone's hotspot — and two laptops on two networks can hold the same private address (192.168.1.23 at two different homes). A lease keyed to the IP address would therefore change as the laptop moves, and could be shared by two laptops. From release 2.5.0-lkvexa.2 the lease belongs to the laptop itself: to a device key derived from the identifier the operating system gives the machine, which no network changes ({{ref:device-identity}}).

PropertyHow it is kept
StaticThe address is leased to the laptop's device key, which is the same on every network and for every user of the laptop, and is pinned in the laptop's device file; every lease table the laptop meets is asked for that address first ({{ref:pin}})

The laptop's identity

The host reads the operating system's own machine identifier:

SystemIdentifierSurvives
WindowsHKLM\SOFTWARE\Microsoft\Cryptography\MachineGuidNetworks, users, updates; not a reinstall of Windows
macOSIOPlatformUUID (from ioreg), bound to the hardwareNetworks, users, updates and reinstalls
Linux/etc/machine-id, else /var/lib/dbus/machine-idNetworks, users, updates; not a reinstall of the system

From it the host derives the laptop's device key, an application-specific digest from which the identifier cannot be recovered:

device key = "device:" ‖ first 32 hex digits of HMAC-SHA-256(key = "RINK-VT device 1", message = lower-case, trimmed machine identifier)
           e.g. the identifier 4c4c4544003910398053b4c04f584e33 gives device:786ccb4ad0fe713fbca602c54b373160

A computer that has no machine identifier receives a random 128-bit key instead, kept in its device file. Wherever the workbench shows a laptop, it shows the first eight digits of its key: device 786ccb4a.

The device file

Each laptop keeps its identity and its pinned address in a device file, one per user, outside every data folder, so that it outlives any league and any copy of RINK-VT:

SystemPath
Windows%LOCALAPPDATA%\RINK-VT\device.json (local application data: it does not roam with a profile)
macOS~/Library/Application Support/RINK-VT/device.json
Linux$XDG_DATA_HOME/rink-vt/device.json, by default ~/.local/share/rink-vt/device.json
AnyThe environment variable RINKVT_DEVICE_FILE, or the host's --device-file

The file is sealed ({{ref:device-format}}). A file that is damaged or edited is replaced, and the start report says so; because the key is derived again from the machine, the laptop keeps the same key and, with a fleet register or any league it has used, the same address. A file made on another computer — copied with a user profile, restored onto a new laptop — is recognised by its key, which is not this machine's, and the laptop receives an identity of its own: two laptops can never become one by sharing a file. A device file that cannot be written refuses the start (exit 7); --device-file then names a place that can be written.

The pool

Leases come from a pool, by default 127.16.0.0/12 (--pool). A pool MUST lie inside 127.0.0.0/8, MUST be a /9 to a /24 starting on its own boundary, and MUST NOT overlap 127.0.0.0/16, which the computer itself uses (127.0.0.1, and 127.0.1.1 on many Linux systems). Addresses ending in .0 or .255 are never handed out. A pool of prefix length n holds

capacity = (2^(32 − n) / 256) × 254          the default /12: 4 096 × 254 = 1 040 384 addresses

and the address at slot i is base + ⌊i / 254⌋ × 256 + (i mod 254) + 1. A laptop's pin belongs to the pool it was given in; a start with another pool treats the pin as absent and says so.

Choosing an address

A laptop's first address is computed from its key alone:

slot(key) = int( SHA-256("RINK-VT loopback 1" ‖ NUL ‖ key)[first 16 hex digits], 16 ) mod capacity
first address = the address at slot(key); if another key holds it, the next slots in order, wrapping (linear probing)

The same key therefore receives the same first address in any empty table: a laptop starting a new league, or a new copy of RINK-VT, lands on the address it had. The example key above receives 127.26.220.77 in the default pool.

The pin

The first address a laptop receives — from its fleet register when it has one, otherwise from the first lease table it meets — is pinned in its device file. From then on, every lease table the laptop meets is asked for exactly that address: a table grants it when no other laptop holds it there. The pin is what keeps a laptop's address the same across leagues even when, in some table, probing would have moved it.

Unique everywhere: the fleet register

A league's lease table guarantees uniqueness among the laptops that have used that league. A club or league whose laptops should never meet on one address, whichever leagues they open, enrols them in a fleet register: one lease table they all share, on a network share or on a removable disk that travels between them.

  1. Choose the register's place, a folder every laptop can reach and write: \\server\rinkvt\fleet-leases or E:\rinkvt\fleet-leases. The folder must exist; the host never creates a register's folder.

  2. On each laptop, start the host once with --fleet naming the register, or enrol it without starting the workbench: RINKVT.cmd leases --enroll E:\rinkvt\fleet-leases (./rinkvt.sh leases … on macOS and Linux).

  3. The register gives the laptop its pinned address if no other laptop holds it there, else the next free one, and the laptop pins the result. Each allocation takes the register's exclusive lock and re-reads it first, so two laptops enrolling at once never receive one address.

  4. The device file remembers the register. Later starts consult it whenever it can be reached; when it cannot — the laptop is at the arena, the disk is in another bag — the pinned address is used, and the report says that the register was unreachable.

Enrolment can change a laptop's address once, when its pin is already another enrolled laptop's; the report says so. From then on the address is fixed.

When two laptops meet on one address

Without a common register, two laptops' first addresses coincide with a probability of about one in a million per pair. If two such laptops then use the same league — a league folder moved from one to the other — that league's table already gives the address to the first. The second laptop receives the next free address in that league, keeps its pin for every other league, and the host warns, in the start report, in the window and in its event ledger:

WARNING: in this league's lease table another laptop holds 127.26.220.77, this laptop's address; here it is 127.26.220.78.
         Enrol every laptop in one fleet register so that no two can meet on one address

Uniqueness within a league always wins over the pin, so the audit trail of a league can never confuse two laptops.

The lease table

A league's lease table is loopback/leases in its data folder (--leases); a fleet register is the same kind of file. Its first line is a header naming the format, the pool and the IPv6 key prefix; each later line is one lease of four fields separated by single spaces: the address, the key, the time it was made (UTC) and a seal — the first 16 hexadecimal digits of the SHA-256 of the first three fields joined by spaces.

# RINK-VT loopback leases · format 2 · pool 127.16.0.0/12 · ipv6 /128
127.26.220.77 device:786ccb4ad0fe713fbca602c54b373160 2026-11-15T18:40:02Z (16-digit seal)

Format 2 holds device keys and IP keys. Format 1, the reference edition's, holds IP keys only; the host reads it, and upgrades it once when it must record a device key: the header is rewritten to name format 2, under the lock, and every lease line is kept byte for byte. A lease line is appended and synced before the address is used. A last line cut off by a stop was never handed out and is dropped when the table is next read. Any other damage refuses the table, and with it the start (exit 7): a line without four fields or not matching its seal; an address outside the pool; a key that is not canonical; a device key in a format 1 table; a second lease for one key or one address; or a header naming another pool or IPv6 prefix.

A lease table and a fleet register MUST NOT be edited. A laptop's lease in them is permanent: a laptop that is retired keeps its line, so that its address is never given to another laptop and the audit trail stays unambiguous.

Reading and enrolling

The host's leases command reads lease tables and enrols a laptop; on Windows it is run as RINKVT.cmd leases …, on macOS and Linux as ./rinkvt.sh leases ….

RINKVT.cmd leases --this-laptop                      this laptop's device, pinned address and fleet register
RINKVT.cmd leases --enroll FLEET_FILE                enrol this laptop in a fleet register and pin its address
RINKVT.cmd leases [--data DIR | --file FILE]         a lease table or register: format, pool, every lease
RINKVT.cmd leases --file FLEET_FILE device:786c…     the address a device key or an IP address holds there

Only --enroll writes: one lease line in the register, and the pin in this laptop's device file. Leases never change or expire.
