Limitations and known boundaries

This chapter states what the release does not do, and where its evidence ends. Each boundary is a fact about this release, not a defect report.

Platforms

  • The release is qualified on the platform its qualification record names ({{q_platform}}). The launchers for Windows (START_RINKVT.cmd, VERIFY_RINKVT.cmd) and the behaviour on macOS are written for those systems from their documented behaviour — Windows answering on all of 127.0.0.0/8, macOS only on 127.0.0.1 — but were not executed for this release.
  • On macOS the host listens on 127.0.0.1 unless the laptop's address is added as an alias; the address is leased and recorded either way.
  • Uniqueness of the laptops' addresses everywhere rests on a fleet register they share. Without one, two laptops are unique in every league they both use, and may — about once in a million pairs — hold the same address in two separate leagues.
  • A reinstall of Windows or Linux changes the machine identifier, and the laptop becomes a new device with a new address; the audit trail keeps the old one on earlier lines.
  • The renderer must be a Chromium-family browser for the isolated app-mode window. The page itself uses standard web platform features, but other browsers were not tested.

Scale

  • The window holds the whole league in memory and replays every ledger when it opens, as the reference edition's offline bench does. A few hundred games are comfortable; the engine caps a league at 1 000 games and a game at 20 000 frames.
  • Loading a league sends every ledger to the window at each opening. For a league of many seasons, a separate data folder per season keeps the opening short.
  • League-wide models refit when the league changes; their cost grows with the number of stints.

Users and concurrency

  • One operator identity, operator@local, with administrative capability; there are no principals, roles or club tenants as in the reference edition.
  • Several windows on one host are supported by refusing the later of two conflicting commits; they do not see each other's changes until they reload.
  • One host per data folder; a data folder belongs to one computer at a time. There is no merge of two copies of a league.

Storage

  • Durability rests on the operating system's fsync and atomic rename. On storage that does not honour them — some network shares, some synchronised folders, some removable media — a power loss can lose or damage more than an unacknowledged last line. Keep the data folder on a local disk (OPS-03).
  • A damaged league refuses to open as a whole; unlike the reference edition, a single damaged game is not quarantined while the rest runs. It is restored from a backup ({{ref:recovery}}).
  • The ledger format differs from the reference edition's; there is no conversion tool in this release.

Engine and laboratory

  • The start frame belongs to this edition's engine ({{engine}}); the reference edition {{reference}} does not have it yet. Games created by 2.5.0-lkvexa.1 have no start frame and start with their first GO.
  • The heat maps use the JavaScript kernel; the reference edition's XPU (WebAssembly) kernel is not part of this edition. Both give the same integers.
  • The models are descriptive under declared assumptions; the NHLe factors are placeholders ({{ref:models}}). HK001 is a synthetic research laboratory with no predictive authority.
  • The engine's own test suite runs in the reference edition; this edition exercises the engine through its browser tests and its store tests on real engine output.

Contracts

  • The JA21 sources are modeled: there is no JA Core parser, compiler or virtual machine, and nothing executes them ({{ref:ja21}}).
  • The MSSL records are checked against the corpus's observed subset; MSSL constructs not demonstrated by the corpus are not used, and no record claims execution semantics the corpus does not define.
