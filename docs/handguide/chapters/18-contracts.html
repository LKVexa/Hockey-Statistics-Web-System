Contracts

The edition describes its components in the LK/Vexa languages: {{n_records}} MSSL records and {{n_ja}} JA21 sources. The descriptions are checked — against the languages' own rules, against the user's own validators, and against the implementation — and they claim no more than their evidence.

Why contracts

A contract states, in a form a machine can check, what a component promises: its interfaces, its invariants, its limits and its maturity. The code is the authority on behaviour; the contract is the authority on what is promised, and the check ties the two together so that neither drifts from the other unnoticed. Appendix F lists every record with its seal and prints the suite's identity record and the four JA21 sources in full.

MSSL records

The records are MSSL 0.3 documents of the observed module/learn subset described by the MSSL Writers Corpus 1.0.0, profile basic_mssl.executable.3. Each has the thirteen fields in their invariant order:

MSSL{ α ≡ header, ι ≡ identity, λ ≡ module, ℛ ≡ ordered rules, π ≡ placements, δ ≡ rule count, τ ≡ 0,
      μ ≡ materialised memory, ρ ≡ results, χ ≡ diagnostics, η ≡ execution projection, ν ≡ extensions, κ ≡ seal }⇒⊤
  • Rule 0001 is module("λ"); each later rule is learn("key",literal("text")), one fact.
  • δ is the number of rules; τ is 0; π, χ and ν are empty, ρ has three empty lists — as in every observed 0.3 document.
  • μ holds every fact as learn.key with its type made explicit (text, number, Boolean, list or object), and η.state holds the same facts without the prefix.
  • κ is sha256: followed by the SHA-256 of the exact UTF-8 text from α≡ up to, not including, the comma of ,κ≡.

The qualification record

tools/contracts.py qualify runs the whole test suite in a fresh interpreter and writes record 90 from what the run showed: the target (the version and the engine version), the result — PASS only when every test passed, BLOCKED otherwise — the numbers of checks, passes, skips and failures, the test modules covered, the command that ran them, the platform (system, release, machine and Python version), the time, and the scope: whether the browser tests ran and in which Chromium, and that other operating systems are not qualified by the record. JA21 sources

The JA21 sources are JA Core 0.3 programs in the provisional grammar of the JA21 JA Core Application Language Suite 1.0.0: the source header ja source 0.3, a module, use Core, policy no_network, then constants, records, enums and functions with effect clauses, and top-level assertions on sample values.

The JA21 sources are modeled contracts. The JA21 suite supplies no JA Core parser, compiler or virtual machine, and this edition does not claim one: nothing executes these files, and the operations they call (Sha256.hex, Crc32c.of and the like) name the implementation's operations rather than a library that exists in JA Core.

What makes them more than prose is the cross-check: every constant they state — the CRC-32C check value, the meta-line magic, the default pool and its capacity, the first lease of 203.0.113.5, a device key and its first address, the store's registry and ledger limits, the token header and the body limit — is compared by tools/contracts.py check with the value the running implementation holds, and a difference fails the check.

Checking with the corpus validators

  1. python -I -B tools/contracts.py check validates every record with the release's own implementation of the corpus's single-document rules, compares records 00–60 with what the generator writes, checks the qualification, checks the JA sources and cross-checks their constants — among them the clock bytes of START and WHISTLE, read from the engine's wire format, and the six overtime presets and the built-in rules, read from the engine's overtime.js.

  2. Add --mssl-verifier <MSSL_WRITERS_CORPUS_1.0.0>/tools/VERIFY_MSSL.py to have the corpus's own validator (its validate_source) check every record as well. The validator is loaded from the user's copy of the corpus and only reads.

  3. The JA sources are checked as the JA Core suite's tools/validate_suite.py checks the suite's own scripts — the source header, module, policy no_network, balanced braces — and, in addition, line 1 must be the header, line 2 the module, every top-level line a declaration or statement of the provisional grammar, brackets and parentheses balanced, and no tab used.

The honesty rule

The MSSL corpus's rule is that status and maturity never exceed the strongest evidence a document names: a specification is not an execution, and a passing component test is not a passing release gate. The records keep it. A component record says OPERATIONAL and names the tests that show it; the suite's record defers to the qualification; the qualification says PASS only when every test passed, and names the one platform on which they ran. A record never claims a platform, a parser or a certification that no evidence shows (MNT-02).
