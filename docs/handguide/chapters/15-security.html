Security

The workbench is one operator's program on one computer. It protects two things: the league on disk, against loss, silent damage and other programs; and the computer, against the workbench being used from elsewhere.

Assets and boundary

AssetWhat must not happen
The league on diskLoss of an acknowledged line; a change no command made; damage that goes unnoticed; two writers at once
The programRunning code the release did not seal
The workbench's APIUse by a web page, another computer or another origin
The operator's browsingThe workbench exposing cookies, sessions or extensions of the ordinary browser, or they exposing the workbench

The boundary of the workbench is the host process, its renderer window and its data folder. Other programs run by the same user on the same computer are inside the computer's boundary but outside the workbench's: they can read the data folder and the page, and the workbench does not defend against them ({{ref:residual}}).

Threats and controls

ThreatControl
A web page in an ordinary browser calls the host (cross-site request, DNS rebinding)The host answers only a Host header that names its lease address and port (421); every API route but health needs the launch's token, which only the host's own page holds (403); a change must be application/json (415) and, with an Origin, the host's own (403). A page of another origin can neither read the token nor send a JSON request the browser would let through without it
Another computer on the networkThe listener is bound to a loopback address only; nothing listens on a network interface
A changed or planted program fileThe code of the release is checked against the manifest before anything opens (exit 4); the launchers run Python in isolated mode, so no user-site or environment path can insert a module; no bytecode is written beside the sealed sources
Script injection into the pageA Content Security Policy of default-src 'self' with no inline script, style or event handler and no eval; frame-ancestors 'none' and X-Frame-Options: DENY; nosniff; text from the league is rendered as text, never as markup
Loss of an acknowledged lineEvery line is written and synced before it is acknowledged; the window shows only what is acknowledged ({{ref:recording}})
Silent damage or an edit of the leagueHash-chained ledgers whose every entry keeps its CRC-32C; a sealed registry; damage refuses to open and is named; store verify and --verify-only re-read everything
Two writersOne host per data folder (exit 5); a stale window's commit is refused (409)
Oversized or malformed inputBodies of at most 32 MiB, no chunked bodies, strict JSON, every entry checked against the engine's seals; roster files are parsed by readers that take time proportional to their input and stop at their limits
The ordinary browser's profileThe window runs on a profile of its own with extensions disabled; the ordinary profile is used only on request
Disclosure through logsRequests are not logged; events never record a request's content; the league stores loopback addresses, not IP addresses

Residual risks

  • A program running as the same user can read the data folder and the page's token. It is inside the boundary of the computer; protecting against it requires the operating system's own controls (separate accounts, disk encryption).
  • The page holds the token for its lifetime; closing the window does not revoke it, stopping the host does (each launch draws a new token).
  • The renderer is the installed browser, and its security is that browser's. An outdated browser is a risk to the workbench as to anything else.
  • On macOS the host listens on 127.0.0.1, which every local program can reach; the Host and token guards still apply.
  • The ledger chain proves that a ledger is internally consistent and unedited since it was written; it does not prove who wrote it. A party able to rewrite the whole data folder could write a different consistent league. Keeping backups elsewhere, and their verification reports, is the control.

Security obligations

SEC-01The operator MUST NOT expose the host's port to a network by any forwarding, proxy or tunnel; the workbench is designed for its own computer only.
SEC-02The operator SHOULD keep the installed browser up to date.
SEC-03The operator SHOULD use the window the host opens, on its own profile, rather than --allow-default-browser-fallback.
SEC-04The operator MUST NOT run a release whose verification fails, and MUST obtain releases from their source and verify them ({{ref:verify}}).
SEC-05Where the league is sensitive, the data folder SHOULD be on an encrypted disk and in an account only the operator uses.
