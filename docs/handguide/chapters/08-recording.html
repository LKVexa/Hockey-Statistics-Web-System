Recording, durability and recovery

The workbench keeps one rule above all others: the window shows a command's result only after the host has written and synced what the command changed. This chapter states the rule, the protocol that keeps it, and what happens when something goes wrong.

The recording rule

A command that changes the league — a scored line, a correction, a new game, a roster import, a simulation — changes the league in the window's memory first, because the engine runs there. Before the command's result is printed, the window sends the host everything the command changed and waits for the host's answer. The host answers only after the change is on disk. If the host refuses or cannot be reached, the window prints NOT RECORDED and the reason, discards its own league and loads the league again from the host. At every moment, therefore, what the window shows as recorded is on disk, and nothing it shows was invented by the window alone.

The commit protocol

  1. The command runs in the engine. The line is compiled and applied; every accepted frame is appended to its game's ledger in memory with its meta line, and a registry change raises the registry's revision.

  2. The window gathers the change. It compares the league with what it last saw recorded: the registry text if the revision changed (serialised as the reference edition serialises it), and, for every game, the ledger entries after the last recorded one, as 128-byte pairs (a frame and its meta line). A ledger always holds whole pairs; an odd count is an error that stops the commit.

  3. The window commits. It sends POST /api/commit with the registry seal it last saw (base), the registry text if it changed, and per game a batch: the game's key and UUID, the index of the first pair (start) and the pairs in base64. A long change, such as a simulation, is sent as several commits of at most about 9 MB of entries each, the registry with the first.

  4. The host admits or refuses. Under its store lock it checks the commit ({{ref:store-checks}}). Nothing is written unless every check passes.

  5. The host writes and syncs. The registry first (when it changed), through its new seal and two renames ({{ref:power-loss}}); then each game's new lines, appended in one write and synced; then a commit event in the event ledger.

  6. The host answers with the new registry seal and each game's count of pairs. The window records them, shows recorded, and the command prints its result.

When a commit is refused

A refusal leaves the disk as it was. The window prints, in red, NOT RECORDED: with the host's reason, sets the host strip to NOT RECORDED, leaves RINK mode, and loads the league from the host again, so that it shows only what is recorded. The command that caused it prints nothing further. If the league cannot be loaded again — the host has stopped — the window says so and asks to be reloaded once the host runs. A line shown as NOT RECORDED is not in the league; to record it, type it again.

Several windows

Several windows may be open on one host; each holds its own copy of the league. Two windows may score different games at the same time. When two windows change the same game, or the registry, the first commit is admitted and the second is refused (check 2 or check 6), and the second window reloads, now showing the first window's change. No interleaving of two windows' entries in one ledger is possible.

Power loss and crashes

The host writes in an order that leaves the disk in a state it can open after a stop at any instant:

  • Ledger lines are appended in one write and synced. A stop during the write leaves a prefix of the lines, the last possibly cut off. A cut-off line — one without its terminating newline — was never acknowledged; opening the league drops it, and the window reports which games had one. Complete lines before it are kept: a commit cut off by a power loss may thus survive in part, as a prefix of what was sent, and after the restart the window shows exactly what is on disk.
  • The registry is replaced in four steps: its new seal is written and synced as registry.sha256.new; the new text is written and synced to a temporary file; the text is renamed over registry.json; the new seal is renamed over registry.sha256, and the folder is synced. A stop before the first rename leaves the old registry with its seal, and the next open removes the leftovers. A stop between the two renames leaves a text that matches the pending seal, and the next open completes the commit.
  • The registry is written before the ledger lines of the same commit, so a ledger never holds entries of a game the registry does not know.
  • Events are appended and synced like ledger lines.

Every acknowledged commit is complete on disk: the answer is sent after the last sync.

Damage

Anything other than a cut-off last line is damage, and the host refuses to open a damaged league (exit 6) rather than open what remains. Damage includes: a registry that matches neither its seal nor a pending one; a ledger line that breaks the chain (a wrong sequence number or previous hash), does not match its own hash, does not hold two 64-byte entries, or fails the engine's seals; a ledger header that names another game, UUID or format; and an event ledger whose chain is broken. The refusal names the file and the line.

An edited file is damage. Editing a ledger or the registry by hand — even to "fix" it — makes the league refuse to open. Restore from a backup instead ({{ref:recovery}}).

Verification

Two commands re-read a league from disk and check every seal and chain, repairing nothing: store verify in the window (and the strip's verify store), which asks the running host, and RINKVT.cmd --verify-only --data DIR (./rinkvt.sh on macOS and Linux), which checks a folder no host has open — a backup, a copy — and skips the league with a note when a host holds it. Recovery procedures

A league that refuses to open

  1. Run RINKVT.cmd --verify-only --data DIR (./rinkvt.sh --verify-only --data DIR on macOS and Linux) and keep the report: it names every damaged file and line.

  2. Move the damaged data folder aside; do not delete it.

  3. Restore the most recent backup of the data folder ({{ref:backup}}) to its place, and verify it the same way.

  4. Start the host. Lines recorded after the backup are not in the restored league; enter them again from the paper record or the scorer's notes.

One damaged game

A damaged ledger of one game may be replaced by that file from a backup, provided the backup's registry holds the same game with the same UUID; the game then holds the entries the backup held. Verify the folder before starting the host.

A lock left behind

A lock whose process is gone is taken over by the next start without action. A lock that names another computer is refused; if that computer no longer uses the folder, remove .rinkvt.lock by hand.

Data custody obligations

DAT-01The operator SHOULD back up the data folder after every session in which games were scored, and MUST keep at least one backup on a different disk ({{ref:backup}}).
DAT-02A backup SHOULD be verified with --verify-only when it is made and before it is restored.
DAT-03A league that refuses to open MUST be restored from a backup, not repaired by hand.
DAT-04The scorer SHOULD keep a paper or written record of a game until its lines are recorded and the league is backed up.
DAT-05The league's lease table SHOULD be backed up with the league, so that every laptop stays unique in it after a restore; a fleet register SHOULD be backed up on its own ({{ref:lease-file}}, {{ref:fleet}}).
