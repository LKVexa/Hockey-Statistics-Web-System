The reference edition

HERMIT + RINK-VT {{reference}} is the edition the engine comes from: a multi-user gateway on Node.js that serves terminals and a browser dashboard to principals with capabilities, keeps the league in SSD-RAM ledgers, and gives every client IP address a static loopback address. It is delivered as an archive, not in the LK/Vexa repository.

What it is

HERMIT is a gateway that serves SPIRAL terminal sessions — each in a worker thread or process with an enforced memory cap — to browsers and to a desktop application. RINK-VT adds the statistics service to it: the same engine as the LK/Vexa edition, run once in the gateway for all clients, with a rink mode in every terminal, a browser dashboard with a command bar, live feeds over WebSocket, and a durable league. Its manual is docs/RINK-VT.md in its archive; this chapter summarises what an operator of the LK/Vexa edition needs to know to work beside it.

Starting it

START.cmd                            Windows
./start.sh                           Linux, macOS
node tools/start-local.js --demo 12  with twelve synthetic games typed into an empty league

The local launcher binds 127.0.0.1:10000, creates a principal for the local operator with administrative capability, and prints its access token once; the browser signs in with it at http://127.0.0.1:10000/. In a terminal, rink enters RINK mode; in the browser, RINK in the title bar or Ctrl+K opens the command bar. League data is kept in .vws-local/rink/, the lease table in .vws-local/loopback/leases.

The gateway refuses to start (EHEAPCAP) when a process-wide V8 heap flag, usually --max-old-space-size in NODE_OPTIONS, would defeat its per-session memory caps. Unset the flag, or set VWS_REQUIRE_HEAP_CAP=0 to run with the cap disclosed as unenforced.

Principals and capabilities

CapabilityAllows
rink.queryGames, leagues, teams, rosters and references; queries; HK001 cases; the tenant's own notes; live updates
rink.scoreThe above, and submitting frames, creating games, and seeing who typed each line (Q AUDIT, operator identities)
rink.adminThe above, and leagues, teams and players, roster import, simulation, ledger verification, every tenant's notes

A principal whose tenant is four letters is a club tenant: it scores and creates only that club's games and sees only its own notes; other tenants are league staff. Subscribers see the server's own description of an accepted line, never text a client supplied; the operator's identity is sent to scorers and administrators only.

The SSD-RAM ledger

The reference edition keeps each game in one file, ledger/<key>-<uuid8>.ssd, following the Plume SSD-RAM-XPU design applied to a 64-byte frame. A header page carries the magic RINKVT-SSDRAM/1, the geometry, the game's UUID and a CRC-32C. Data lives in segments of out-of-place pages: generation g of a page is written to slot g mod 2, and 64-byte records (CPR1, page, generation, lines, the page's SHA-256, frames, CRC-32C) say which generation is committed. A flush writes every touched page to its other slot and syncs, then writes the records one page at a time in page order, each synced, so whatever survives a power cut is a prefix. The service flushes after every command line before it answers. A torn record falls back to the previous generation; a committed generation whose data no longer matches is reported as damage; a damaged game is quarantined — answered with the reason and left out of league-wide answers — while the rest of the league runs. The entries are the same frame and meta-line pairs the LK/Vexa edition keeps ({{ref:frame}}, {{ref:meta}}), and the registry is the same sealed document ({{ref:registry}}).

Static loopback leases in wide use

A gateway that other computers can reach (VWS_HOST not a loopback address; the default is 0.0.0.0) gives every client IP address that signs in a lease from the same pool and by the same slot function and probing as {{ref:loopback}}; unlike the LK/Vexa edition, it keys a lease to the client's IP address, because a browser or terminal connecting to it does not present a device identity. A session sees its lease as its own host address (hostname -i, /etc/hosts mapping hermit to it, $LOOPBACK, a line of the banner); every line typed records it in its meta line; the logs name a connection by it and never by its IP address; /live counts leases and names none.

SettingDefaultMeaning
VWS_LOOPBACK_FILE—The lease table. Required in wide use: without it the gateway refuses to start, so that "static" survives a restart
VWS_LOOPBACK_POOL127.16.0.0/12Where leases come from (the rules of {{ref:pool}})
VWS_LOOPBACK_MAX_LEASES65 536The most client addresses; a new client beyond it is refused (503), never given another's address
VWS_LOOPBACK_IPV6_PREFIX128128: each IPv6 address is a client; 64: an IPv6 client is its /64 (privacy addresses change daily)
VWS_LOOPBACK_VOLATILE01 accepts wide use without a file: a client that collided with another may get another address after a restart
VWS_TRUST_PROXY—The proxies in front of the gateway, as a count (1–8) or their addresses and networks. Unset, the socket's peer is the client and X-Forwarded-For is ignored; set, the header is read through those proxies only, and an address a client wrote into it itself is never believed. Unreadable forwarding is refused (400)

node tools/loopback.js FILE [ADDRESS] lists the table or maps one address to the other. Behind a proxy or load balancer, set VWS_TRUST_PROXY or every client shares the proxy's lease; compare hostname -i from two computers before relying on it.

Deployment

deploy/Dockerfile copies the gateway with ram/, rink/ and vendor/xpu/, keeps the lease table and the league under a /data volume (VWS_LOOPBACK_FILE=/data/loopback/leases, VWS_RINK_DIR=/data/rink), and tools/docker-files-check.js starts the gateway from exactly the files the Dockerfile names — in wide use, with a session and a statistics command — without Docker. deploy/render.yaml gives the service a disk at /data and trusts one proxy.
