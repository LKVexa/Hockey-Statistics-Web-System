Data formats

Every byte the workbench keeps has a defined layout and a seal. This chapter is the normative description of each format: the frame and its meta line, the registry, the game ledger, the event ledger and the release manifest.

The 64-byte frame

A frame is one fact, exactly one cache line long. The engine compiles every line to frames, and the frames are what the ledger keeps: the statistics are always computed again from them. All integers are big-endian.

BytesFieldContent
0–15UUIDA UUIDv7 (RFC 9562): the frame's identity. A frame received twice answers DUPLICATE
16–23OnsetThe keystroke onset, nanoseconds since the Unix epoch: the time at which the event latches the clock
24–31CommitThe time Enter was pressed, nanoseconds; never before the onset, and at most 5 s ahead of the service's clock
32–35GameThe first four bytes of the game's UUID: a frame belongs to exactly one game
36–39LamportA Lamport counter, increased by the compiling client with every frame
40–43TEAMThe team code, four ASCII letters; in a system frame, ! and a three-letter opcode
44–47PLAYERThe player code, ASCII, NUL-padded
48–51STATThe stat token, ASCII, NUL-padded
52–55MODThe modifier, at most four ASCII characters in canonical order, NUL-padded
56–59x, yTwo signed 16-bit integers in tenths of a foot; −32 768 in both means "no coordinates" (the zone centroid or the specification's prior applies)
60–63CRCCRC-32C (Castagnoli) of bytes 0–59

System frames

A system frame carries ! and an opcode in bytes 40–43: !UND (undo), !DEL (delete an event), !FXP, !FXS, !FXC, !FXA (the patches of FIX: player and team, stat and modifier, coordinates, assists), !LIN and !LIA (a lineup and its continuation), and !CLK (a clock command).

Strict decoding

A frame is untrusted bytes, so it is decoded strictly: every text field is canonical — A–Z and 0–9, NUL-padded, nothing after the first NUL; coordinates are both present or both absent and on the 200 × 85 ft ice; a clock time is at most 20:00, a period at most 12, an assist slot 1 or 2. The actor then checks the stat and modifier against the lexer's grammar, canonical order included. A frame that fails is rejected as malformed and nothing it held is echoed; the audit trail shows (malformed frame).

The 64-byte meta line

Each accepted frame is stored with a meta line: who entered it, when it was received and from where. The meta line is what lets a replay apply each UNDO against the operator who typed it. Its integers are little-endian.

BytesFieldContent
0–3MagicCMT1, the unsigned integer 0x31544D43
4–7IndexThe entry's index in the game's ledger
8–15ReceivedThe time the service received the frame, nanoseconds since the Unix epoch
16–19SourceThe source as an ASCII digit, NUL-padded: 0 terminal, 1 web, 2 sim, 3 replay, 4 api, 5 test. The workbench's own lines are terminal lines
20–51OperatorThe operator's identity, ASCII, NUL-padded (operator in this edition)
52–55LoopbackThe four octets of the static loopback address of the computer that typed the line (127.x.y.z), or zeros ({{ref:loopback}})
56–59SpareZeros
60–63CRCCRC-32C of bytes 0–59

The registry

The registry is one JSON document, league/registry/registry.json, written whole at every change, serialised with one-space indentation and a final newline, and sealed by registry.sha256, which holds its SHA-256 and the name registry.json in the form sha256sum -c reads.

MemberContent
schemarinkvt.registry.v1; a registry of another schema is not opened
leaguesLeagues: code, English and French names, abbreviation
teamsTeams: code, names, arena, city, time zone, league
playersPlayers: team, code, names, jersey, position, hand, birth date, import flag
gamesGames: key (G1 …), UUID, home and away, date, season, stage, starters, creation time and identity hash
notesNotes on teams, by tenant
seqThe counters from which game keys and note identifiers are drawn

The host checks the members it depends on ({{ref:store-checks}}); the engine validates the rest when it adopts the registry: names are single-line text without control characters, dates are real calendar dates, a jersey is 1–99, a hand is L or R.

Game ledger files

Each game has one ledger file, league/ledger/<key>-<uuid8>.jsonl, where uuid8 is the first eight hexadecimal digits of the game's UUID. It is a sequence of lines of compact JSON, each ended by LF. The first line is the header:

{"ledger":"rinkvt.vec1-ledger.v1","game":"G1","uuid":"3913755b-7df0-56f3-a423-d01281f42143","created":"2026-11-15T17:26:16.214512Z"}

Every later line holds one ledger entry pair — a frame and its meta line — and the chain:

{"n":0,"frame":"(128 hex digits)","meta":"434d5431…(128 hex digits in all)","prev":"…","hash":"…"}
MemberContent
nThe pair's index, from 0, without gaps
frameThe 64-byte frame, as 128 lower-case hexadecimal digits
metaThe 64-byte meta line, likewise
prevThe hash of the line before; for n = 0, the genesis value below
hashSHA-256(prev ‖ LF ‖ frame ‖ meta ‖ LF ‖ decimal n), over the hexadecimal texts
 
genesis(key, uuid) = SHA-256("RINK-VT ledger 1" ‖ NUL ‖ key ‖ NUL ‖ uuid)
hash_n             = SHA-256(prev_n ‖ LF ‖ frame_hex_n ‖ meta_hex_n ‖ LF ‖ decimal(n)),   prev_0 = genesis, prev_n = hash_(n−1)

A ledger is valid when its header names its game, UUID and format, every line has exactly these five members, its sequence and previous hash continue the chain, its hash is right, both entries are 64 bytes, and the pair passes the engine's seals (the frame's CRC-32C and game, the meta line's magic and CRC-32C). The chain's last hash, the tip, summarises the whole ledger: store verify prints its first digits.

The event ledger

events.jsonl records what the host did, chained like a ledger:

{"seq":9,"at":"2026-11-15T17:28:42.113413Z","event":"commit","detail":{"registry":true,"pairs":3939,"games":["G2","G3","G4","G5"]},"prev":"…","hash":"…"}

The hash of a line is SHA-256(prev ‖ the compact JSON, with sorted keys, of its seq, at, event and detail); the first prev is SHA-256("RINK-VT events 1"). The events are start (version, lease, address bound, port), commit (whether the registry changed, the number of pairs, the games), stop, and internal_error (where, and the error's type — never a request's content).

The release manifest

RELEASE_MANIFEST.json holds the product, edition, version, engine version, the time it was generated, and files: an object mapping every file of the release — paths relative to the release folder with forward slashes — to its SHA-256. It omits itself, .git, runtime, __pycache__, node_modules, .pytest_cache and compiled Python files. The code scope (checked at every start) is the files under photon/, ui/ and engine/, listed or not; the all scope (checked by a verification) is every file.
